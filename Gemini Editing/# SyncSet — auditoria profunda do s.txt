## Bug #1 — Logo genérica no lugar da marca real — ✅ CORRIGIDO E VERIFICADO AO VIVO

`favicon.svg` (placeholder de scaffold) estava sendo usado como marca em 3 lugares
(Header, compass "The core", núcleo de "How it runs"). A marca real já existia em
`public/apple-touch-icon.png`, só não estava ligada a nada. Gerei `logo-mark.png`

referências. Confirmado com zoom no header e no núcleo do diagrama — nítido, zero
erro de console.

## Bug #2 — Cal.com em branco em `/book` — ✅ CORRIGIDO E VERIFICADO AO VIVO

`book.astro` usava `<iframe src="https://cal.com/...">` cru, bloqueado pelo Cal.com
(proteção padrão contra clickjacking de terceiros). Troquei pelo embed oficial deles
(script `postMessage`, `Cal.ns["30min"]("inline", {...})`). Confirmado ao vivo: `/book`
mostra o calendário completo, mês real, horários reais, clique reconhecido.

## Bug #3 — Ícones "duplicados" na faixa de conectores — ✅ CAUSA RAIZ REAL
## ENCONTRADA E CORRIGIDA (minha primeira tentativa estava errada)

**Minha primeira hipótese nesta auditoria (marquee-seam por largura de viewport)
estava errada** — medi ao vivo e descartei, documentado na versão anterior deste
arquivo. **O Paulo então mandou print real do celular dele, que mostrou o bug de
forma inequívoca**: cada ícone aparecia como um par idêntico lado a lado (S-S,
M-M, círculo-círculo, ...), não como uma repetição distante no loop do carrossel.

**Causa raiz real, no código:** `index.astro` linha 387 (antes da correção) fazia
```js
[...21 apps].flatMap((app) => [app, app])
```
`.flatMap(app => [app, app])` duplica **cada item individualmente e adjacente**,
produzindo `[app1, app1, app2, app2, app3, app3, ...]` — não é o padrão de marquee
correto. O padrão certo (duplicar a *lista inteira* uma vez, para o loop de
`translateX(-50%)` funcionar) é `[...lista, ...lista]`, produzindo
`[app1, app2, ..., app21, app1, app2, ..., app21]`. Eu tinha lido essa linha antes e
não simulado mentalmente o `flatMap` corretamente — assumi que already fazia a
duplicação certa e fui atrás de uma causa raiz errada (timing de animação) em vez do
bug real, que era determinístico e sempre visível, sem depender de a animação estar
rodando ou não.

**Correção aplicada:** extraí a lista de apps para uma constante `connectorApps` no
frontmatter e troquei o render para `[...connectorApps, ...connectorApps].map(...)`.

**Verificado ao vivo por inspeção direta do DOM** (não por screenshot — um efeito
colateral de zoom/renderização que introduzi na janela do Chrome do Paulo ao testar
redimensionamento para mobile impediu screenshots limpos depois disso; ver nota no
fim): script no console lendo `data-logo` de todos os 42 `.app-tile` confirmou
`total: 42` e `isImmediatePairBug: false` — nenhum par adjacente idêntico. Lista
começa `googlecalendar, hubspot, notion, stripe, gmail, xero, airtable, make,
telegram, shopify, ...`, ordem correta, sem repetição imediata.

## Bug #4 (novo, achado pelos prints do celular) — Diagrama de fluxo ilegível no
## mobile — ✅ CORRIGIDO, verificação visual pendente

**O que os prints mostraram:** na seção "How it runs", em vez do SVG manter 780px de
largura mínima com scroll horizontal (como o CSS já previa:
`.flow-scroll { overflow-x: auto }` + `.flow-scroll svg { min-width: 780px }`), o
diagrama inteiro aparecia encolhido para caber nos ~380px de tela do celular, com todo
o texto (rótulos dos nós, "Capture/Qualify/Confirm/Route") ilegível, borrado, quase
impossível de ler.

**Causa raiz provável:** o `<svg>` do diagrama tinha `viewBox="0 0 1060 400"` mas
**nenhum atributo `width`/`height` próprio** — só a viewBox e o CSS. SVG sem
`width`/`height` intrínsecos tem comportamento de dimensionamento inconsistente entre
navegadores (principalmente em mobile) quando combinado com `width:100%` +
`min-width` via CSS — em vez de respeitar o `min-width:780px` e deixar o contêiner
pai rolar horizontalmente, alguns navegadores escalam o SVG inteiro pela `viewBox`
para caber no espaço disponível, ignorando o `min-width`.

**Correção aplicada:** adicionei `width="1060" height="400"` como atributos diretos no
`<svg>`, junto da viewBox já existente — isso dá ao elemento um tamanho intrínseco
bem definido, tornando o `min-width:780px` do CSS confiável entre navegadores.

**Não confirmado visualmente ainda:** ao tentar validar no Chrome real do Paulo
redimensionando a janela para simular mobile, o `resize_window` desta sessão causou um
efeito colateral — uma janela do Chrome dele ficou com o conteúdo renderizando
minúsculo (zoom/device-scale-factor preso em ~3x), e eu não consegui reverter isso de
forma limpa fechando/reabrindo abas. **Não mexi mais nisso para não piorar.** A
correção em si (atributos width/height no SVG) é uma prática padrão, documentada e de
baixo risco, mas a confirmação visual final no mobile real depende do próximo print do
Paulo depois que ele testar.

## Lição registrada (atualizada)

Três coisas aprendidas nesta sessão sobre verificação:
1. Verificação de UI = existe + é o conteúdo certo + funciona de ponta a ponta.
2. Quando uma hipótese de causa raiz não se sustenta com números medidos, descartar
   abertamente em vez de forçar uma correção especulativa.
3. **Nova, desta rodada:** ler código complexo (como `.flatMap(app => [app, app])`)
   exige simular mentalmente o resultado passo a passo, não reconhecer o padrão de
   relance e assumir que está certo. A primeira leitura desse `flatMap` pareceu, à
   primeira vista, "duplicar a lista para o marquee" — só simulando de verdade (item
   por item) é que fica claro que duplica cada item individualmente. Isso custou uma
   rodada inteira de investigação na direção errada. Prints reais do usuário venceram
   uma teoria de código elegante, mas errada — evidência empírica sempre helps mais
   que dedução a partir do código quando as duas divergem.
